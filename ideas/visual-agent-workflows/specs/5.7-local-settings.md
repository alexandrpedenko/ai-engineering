# Slice 5.7 — a local settings file

**Status:** built (2026-10-11), in review.

**Capability.** Choose the project and the default agent provider once, in a
file next to the orchestrator, instead of environment variables on every
command:

```jsonc
// workflow-orchestrator/settings.json   (gitignored; copy settings.example.json)
{
  "projectRoot": "/Users/me/code/booking-app",
  "runtime": "claude",
  "models": { "claude": "claude-sonnet-5-5" }      // optional
}
```

```
$ npm run dev          → works on /Users/me/code/booking-app with Claude
$ npm run wf -- run ba-discovery
$ npm run scan
```

The simple version of [proposal-settings-and-projects.md](proposal-settings-and-projects.md):
no settings UI, no project registry, no provider switch in the browser. Edit
the file, restart.

## Two files, two owners

| file | committed | holds |
| --- | --- | --- |
| `orchestrator.config.json` | yes | how projects are laid out: workflows dir, skill and agent dirs, artefact globs, data dir |
| `settings.json` | **no** (gitignored) | this machine's choices: `projectRoot`, `runtime`, `models` |
| `.env` | no | API keys, as before |

`settings.example.json` (committed) shows the three keys. `settings.json`
accepts only those three; anything else is an error naming the key and the
file. `projectRoot`, `runtime` and `models` are removed from the committed
`orchestrator.config.json` (their defaults still apply when neither file sets
them; the config file may still set them, for the drop-in case of ADR-0001).

## Precedence

For each of `projectRoot`, `runtime`, `models.<runtime>`, the first that is set wins:

1. a command-line flag (`--project`) or environment variable (`ORCH_PROJECT_ROOT`,
   `ORCH_RUNTIME`): unchanged, so `dev:sample`, tests and one-off runs still work
2. `settings.json`
3. `orchestrator.config.json`
4. the defaults (`..`, `cursor`, `composer-2.5` / `claude-opus-5-5`)

A relative `projectRoot` in `settings.json` resolves against the orchestrator
folder, like the config's; an absolute path is clearer.

## What changes

- **core**: `domain/settings.ts` (`LocalSettings` schema: the three optional
  keys, strict). `loadConfig` reads `settings.json` after the config and
  applies the precedence above; a bad settings file is an
  `InvalidConfigError` naming `settings.json`.
- **server**: the server's start line and `npm run wf` say which project and
  runtime they use and where that came from (`settings.json`, environment, or
  defaults), so a wrong project is obvious at once.
- **files**: `settings.example.json`, `.gitignore` gains `settings.json`,
  `orchestrator.config.json` loses the three keys.
- **docs**: README setup steps; architecture docs `project-registry` and
  `composition`.

No new dependencies. No UI changes.

## Tests

| file | checks |
| --- | --- |
| `core/tests/domain/settings.test.ts` | the three keys parse; empty is fine; an unknown key or a bad runtime fails |
| `core/tests/infrastructure/loadConfig.test.ts` | no settings file → as before; settings beat config; overrides (env/flag) beat settings; `models` merge per runtime; a relative `projectRoot` resolves from the orchestrator folder; bad JSON / unknown key → `InvalidConfigError` naming `settings.json`; the result says where `projectRoot` and `runtime` came from |
| `server/tests/cli/wfCommand.test.ts` | the run line names project and runtime |

## Done when

- `npm run check` passes.
- With a `settings.json` pointing at a copy of the sample project and
  `"runtime": "claude"`: `npm run scan` lists that project; `npm run dev`
  shows "runtime: claude" in the app bar; no environment variables needed.

## Amendments

**2026-10-11, slice 5.7 build — where the "which project, which runtime" line lives.**
Spec said: the server and `npm run wf` print which project and runtime they use.
Now: `describeSetup(config, fake)` in `server/src/composition.ts`;
`createRunServices` exposes it as `setup`, which `npm run wf` prints before
the run (not for `status`); the server prints it after its address.
`ResolvedConfig.sources` is optional in the type (only `loadConfig` fills it).
Why: a separate file at `server/src/` root belongs to no layer
(architecture test).

**2026-10-11, slice 5.7 review — tests no longer read the developer's settings.json.**
Spec said: nothing about tests.
Now: `ORCH_SETTINGS_FILE` names the settings file (default
`workflow-orchestrator/settings.json`); `vitest.config.ts` points it at a file
that doesn't exist, so every test starts from defaults.
Why: with a real `settings.json` (runtime claude) two tests that expect the
default runtime failed. Found when the first real settings file was written.
