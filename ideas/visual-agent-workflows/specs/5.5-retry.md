# Slice 5.5 — retry a failed step

**Status:** spec drafted, in review (2026-10-11). Not built.

**Capability.** When an agent step fails (the agent errored, it was
cancelled, or its process stopped), run that step again as a new attempt
and carry on from there, instead of starting the whole run over. From the
browser (a **Retry** button on the failure banner) and from the terminal
(`npm run wf -- retry <runId>`).

```
run-6585   BA discovery · failed at design: rate limited          [ Retry ]
  ✓ elicit   attempt 2
  ✓ review   approved
  ✗ design   attempt 1 · failed: rate limited
        ↓ Retry
  ▸ design   attempt 2 · running …
  ✓ design   attempt 2 · created discovery/design.md        → finished
```

Follows [../spec.md](../spec.md), ADR-0003 (the engine), ADR-0006 (no second
agent run for one attempt), ADR-0012 (tests on every side). Builds on slices
2–5.

## How it works

- **Only a `failed` run can be retried**, and only its failed step. A gate
  can't fail; an `interrupted` run uses Continue; a `rejected` run ran out of
  revisions on purpose and isn't retried.
- **The engine re-enters the failed step** with LangGraph's
  `Command({ goto: stepId })` on the run's thread. Prototyped on 2026-10-11
  (`@langchain/langgraph` 1.4.21): on a finished thread it runs the named node
  and then follows the edges as usual.
- **It's a new attempt.** The step's attempt number is its earlier runs plus
  one (`cursorRunIds.length + 1`), so it gets its own run ref, idempotency key
  and before-snapshot (ADR-0006, ADR-0007). Files the failed attempt half-wrote
  count as the starting point: the new attempt's writes are measured from
  the files as they are when the retry starts.
- **Nothing else is reset.** Inputs and reviewer feedback for the step are kept,
  so the message is the same as for the failed attempt (plus anything the
  person edited in skills or agents since, because the registry is re-scanned
  per step). The failed record stays in the run state until the new attempt
  finishes and replaces it.
- No retry limit: each retry is a deliberate click or command.

## What gets added

| package | change |
| --- | --- |
| core | `RunEngine.retry(runId, workflow)` (port) and `LangGraphRunEngine.retry`: `ConflictError` unless the outcome is `failed`, then `invoke(new Command({ goto: stepId }))` and settle as usual. `retryRun(deps, runId)` use case (for the CLI). `RunSupervisor.retry(runId)`: checks it's `failed` and idle, then runs in the background like resume. |
| server | `POST /api/runs/:runId/retry` → `202`; `409` when the run isn't failed or is busy; `404` unknown. CLI: `npm run wf -- retry <runId>` retries, then asks at gates as `run` does. |
| web | `OrchestratorApi.retry(runId)`, `HttpOrchestratorApi.retry`, `useRetryRun` (in `mutations.ts`), a **Retry** button on the failed banner of `RunPage`. The timeline already shows the attempt number. |
| docs | `docs/architecture/engine.md` and `runs-and-events.md` describe retry; `http-api.md` lists the route. |

No new dependencies. No new event types: a retry shows as `step-started` with
the next attempt number, then the usual events.

## Contract changes (spec.md amendments when built)

1. `RunEngine` gains `retry(runId, workflow)`.
2. The server API gains `POST /api/runs/:runId/retry`.

## Done when

- `npm run check` passes.
- In `dev:sample`: make the fake agent fail once (a scripted reply, or Cancel
  during a step), see the failed banner, press **Retry**, see the step run as
  attempt 2 and the run continue.
- The architecture docs describe retry.

## Not in this slice

- Retrying from an earlier step ("go back to elicit and redo everything after
  it"). That's time travel on the checkpoint history; a later idea.
- Changing the step's message for a retry (e.g. telling the agent why the last
  attempt failed). Possible later as a prompt section; the failure is often
  not the agent's fault (rate limit, cancel, a stopped process).
