# Slice 5.8 — artefacts anywhere in the project

**Status:** built (2026-10-11), in review.

**Capability.** A project where artefacts live in `kb/` and `ux-space/`
instead of `wiki/` and `discovery/` works with no orchestrator config. A step
whose skill says "write the user flows to `ux-space/flows.md`" and whose
workflow step names no `writes` runs, its record lists `ux-space/flows.md` as
created, and the gate after it shows that file.

```jsonc
// .cursor/workflows/ux.json — the step says who and which skill, not where
{ "id": "flows", "type": "agent", "agent": "designer", "skills": ["user-flows"],
  "instructions": "Map the booking flows from the requirements." },
{ "id": "review", "type": "gate", "onReject": "flows" }   // no "shows": it shows what "flows" changed
```

Decision and reasons: [ADR-0014](../adr/0014-skills-own-artefact-locations.md).

## What changes

**core / domain**
- `config.ts`: `artefactGlobs` is optional, with no default (unset means
  "every markdown or text file").
- `validate.ts`: drops the warning "writes no files, so its result can't be
  checked".
- `buildPrompt.ts`: a step with no `writes` gets one line under `# Rules`:
  "Write your results where the skills above and the project's rules say."
- New `gateFiles(workflow, gate, state) → string[]`: the gate's `shows` if it
  has any. Otherwise the files created or modified by the agent steps on the
  path from `gate.onReject` up to the gate, in their latest attempt, in step
  order, without duplicates. Deleted files aren't included (they're in the
  step timeline already).

**core / application**
- `ProjectFiles` port:
  - `snapshot(declared: string[])` hashes every project file (see below);
    `matches` is filled only for the `declared` patterns. Same `Snapshot`
    type.
  - `isEditable(path)` becomes `async canOpen(path): Promise<boolean>`.
  - `artefacts()` lists from the project file list.
- `runAgentStep`: passes only `step.writes` to `snapshot`; `artefactGlobs`
  leaves `AgentStepDeps`.
- `projectFile.ts`: uses `canOpen`. The error message says "not a file of
  this project the orchestrator can open".

**core / infrastructure**
- `FsProjectFiles`:
  - The **project file list** comes from
    `git ls-files -z --cached --others --exclude-standard` when the root is
    inside a git work tree. Otherwise it walks the root, skipping `.git/` and
    `node_modules/`. Either way the orchestrator folder is removed.
  - `snapshot` hashes every file in the list. Files over 5 MB get
    `size:mtimeMs` instead of a content hash.
  - `artefacts()`: from the list, `*.md`, `*.mdx`, `*.txt` outside the skill,
    agent and workflow folders, narrowed by `artefactGlobs` when it is set.
  - `canOpen`: the path is normalised and inside the root (same checks as
    today), is in the list, and isn't `.env` or `.env.*`.
- `LangGraphRunEngine.gateNode`: the pause carries `gateFiles(...)` instead
  of `gate.shows`. The web and the CLI already show whatever list the
  `gate-waiting` event carries, so neither changes.

**server**
- `main.ts`: listens on `127.0.0.1`.
- `composition.ts`: stops passing `artefactGlobs` to the step runner.

**files**
- `orchestrator.config.json` loses `artefactGlobs`.
- Architecture docs: `project-registry.md` (artefacts, file list),
  `agent-steps.md` (snapshot, prompt rule), `runs-and-events.md` (gate
  files).

No new dependencies (git is called through `node:child_process`). No web
changes.

## Done when

- `npm run check` passes.
- On a copy of the sample project with `wiki/` renamed to `kb/`, a
  `ux-space/` skill whose body names `ux-space/flows.md`, and a workflow step
  with no `writes` followed by a gate with no `shows`: `npm run scan` lists
  `kb/README.md`. A real run (Claude runtime) writes `ux-space/flows.md`, and
  the gate in the browser shows it. No change to `orchestrator.config.json`.

## Not in this slice

- Named locations (`{{paths.kb}}`) for workflows shared across projects
  (ADR-0014, Alternatives).
- Grouping artefacts by folder in the project view.
- Showing deleted files at the gate, or diffs (slice 8).

## Amendments

**2026-10-11, slice 5.8 build — git only when it doesn't ignore the project.**
Spec said: the project file list comes from `git ls-files` "when the root is
inside a git work tree".
Now: only when the root is inside a work tree **and** that repository doesn't
ignore the root (`git check-ignore`). Otherwise the folders are walked.
Why: `npm run dev:sample` works on `.data/sample-project`, which sits inside
this repository but is gitignored there; `git ls-files` returned nothing for
it, so the project looked empty.

**2026-10-11, slice 5.8 build — the web reads the gate's files from the run.**
Spec said: "The web and the CLI already show whatever list the
`gate-waiting` event carries, so neither changes. No web changes."
Now: the CLI needed no change, but the run page took the gate's files from the
workflow step's `shows`. `stepTimeline` now gives a waiting gate's row
`shows` from the run outcome, and `RunPage` uses that. `GatePanel` says "No
files were changed before this gate." when the list is empty. The workflow
page's step list says "writes where its skills say" and "review of the files
changed before it" instead of "nothing". The Vite dev proxy targets
`127.0.0.1`, to match the server's new address.
Why: without it, a gate with no `shows` showed no files in the browser.

**2026-10-11, slice 5.8 build — `/api/files` opens existing files only.**
Spec said: `canOpen` accepts a path that "is in the list".
Now: as specified, which means a path that doesn't exist yet is refused (400)
instead of being created by `PUT` or answered with 404 by `GET`.
Why: the project file list holds only existing files. Nothing in the web app
creates files today; slice 7 (file editor) decides whether "new file" is
needed.

**2026-10-11, slice 6 review — `canOpen` refuses symlinks out of the project and more secret files.**
Spec said: `canOpen` accepts a path in the project file list that isn't
`.env` or `.env.*`; the walk lists every file.
Now: the path's real location (after symlinks) must be inside the project
root; files that commonly hold credentials are refused too (`.envrc`,
`.npmrc`, `.pypirc`, `.netrc`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, SSH keys,
anything under `.ssh/`, `.aws/`, `.gnupg/`); the walk (hosts that aren't git
work trees) doesn't follow symlinks.
Why: the security review showed that a symlink committed in a project
(`docs/notes.md -> ~/.zshrc`) let `/api/files` read and write outside it, and
that `.env*` was too narrow a list.
